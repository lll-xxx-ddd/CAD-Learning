## 可直接发布的精简正文

最近研究了一个很有意思的开源项目：`text-to-cad`。

你只要说：

> 做一块 100 × 60 × 6 mm 的安装板，四角开孔，中间挖一个矩形槽。

AI Agent 就能生成可继续修改、测量甚至制造的 STEP 模型。

但它并不是让大模型直接“捏”出一个 3D 文件。真正的原理是：

> **AI 写 CAD 程序，专业 CAD 内核负责精确建模。**

整个过程大致是：

```text
自然语言 / 图片
→ CAD Brief（结构化设计意图）
→ 尺寸、基准、Feature 参数
→ build123d Python 源码
→ Open Cascade 生成 BREP
→ 输出 STEP
→ 测量 + 几何检查 + 视觉检查
→ 不合格就改源码，再生成一次
```

这里的 Skill 也不是一个重新训练的大模型，更像是交给 AI 的“机械设计操作手册”：告诉它怎么拆需求、怎么安排建模顺序、怎么生成 STEP，以及出错后怎么验证和修改。

为什么不直接生成 STEP？

因为 STEP 保存的是实体、面、边、圆柱、曲面等精确工程几何，不是一堆“看起来差不多”的三角形。直接生成既不稳定，也很难修改。

换成参数化 Python 源码后，设计就变成了 **CAD-as-Code**：

- 看得懂模型是怎样构造的；
- 改一个参数就能调整尺寸；
- 同一份源码可以反复生成；
- 最终几何还能重新测量和验证。

这也是它和很多 Text-to-3D 工具最大的区别：

```text
Text-to-3D：Prompt → Mesh，重点是视觉上像不像
text-to-cad：Prompt → 参数 → BREP → STEP，重点是工程上对不对
```

更关键的是，代码成功运行并不代表 CAD 正确。项目还会检查：有没有有效实体、模型是否闭合、尺寸是否准确、孔是否打对位置、装配是否穿插……

一旦发现问题，就回到参数化源码继续修改。

很像软件开发里的：

```text
写代码 → 编译 → 测试 → Debug → 再编译
```

只不过这次“编译”出来的是 CAD。

所以 `text-to-cad` 最有启发的一点，不是让 AI 取代 CAD 内核，而是让 AI 学会使用 CAD 内核。

它背后的通用公式是：

> **LLM + 领域 Skill + 确定性工具 + 验证闭环**

这套思路也可能扩展到 CAE、CAM、机器人和 EDA 等对精度要求很高的工程领域。

## 长图文完整版

最近研究了一个很有意思的开源项目：`text-to-cad`。

你只要描述：

> 做一块 100 × 60 × 6 mm 的安装板，四角开孔，中间再挖一个矩形槽。

AI Agent 就能生成一个可继续修改、测量和制造的 STEP 模型。

但它的核心，并不是让大模型直接“捏”出一个 3D 文件。

真正的思路是：

> **让 AI 写 CAD 程序，再让专业 CAD 内核负责精确建模。**

这也是我觉得它最值得关注的地方。

### 01｜这个 Skill 到底是什么？

它不是一个重新训练的 Text-to-CAD 大模型，更像是交给 AI Agent 的一套“机械设计操作手册”。

这套 Skill 会告诉 AI：

- 怎样把自然语言整理成设计需求；
- 怎样提取尺寸、基准和特征；
- 怎样组织参数化源码；
- 怎样生成 STEP；
- 怎样检查尺寸和几何；
- 发现错误后怎样修改并重新生成。

换句话说，它给 AI 补上的不只是工具，而是一套 CAD 工程方法。

### 02｜一句话，是怎样变成 CAD 的？

完整链路大致是：

```text
自然语言 / 图片
        ↓
CAD Brief（结构化设计意图）
        ↓
尺寸、基准、Feature 参数
        ↓
build123d Python 源码
        ↓
Open Cascade 精确几何计算
        ↓
BREP / STEP
        ↓
测量 + 几何检查 + 视觉检查
        ↓
不合格就修改源码，再生成一次
```

这里的分工非常清楚：

- **LLM / Agent**：理解需求、规划建模步骤、编写和修改代码；
- **build123d**：用 Python 表达参数化建模过程；
- **Open Cascade**：完成布尔运算、曲面和拓扑等精确计算；
- **Inspect / Viewer**：检查尺寸、几何有效性和外观；
- **STEP**：把结果送进后续 CAD、CAE、CAM 或制造流程。

大模型负责“想”和“写”，成熟几何内核负责“算”。

### 03｜为什么不让 AI 直接生成 STEP？

因为 STEP 不是一段看起来合理的文本，也不只是一个三角网格。

它保存的是精确的工程几何：实体、面、边、圆柱、曲面、装配关系……这些对象必须满足严格的拓扑规则。

让大模型直接输出最终几何，既不稳定，也很难修改。

而生成参数化 Python 源码有三个明显优势：

1. **可解释**：能看到每个实体和孔是怎样建出来的；
2. **可修改**：想把宽度从 100 改成 120 mm，通常只需改一个参数；
3. **可复现**：同一份源码可以反复生成和验证模型。

这其实就是一种 **CAD-as-Code**：像维护代码一样维护机械设计意图。

### 04｜它生成的不是“看起来像”，而是“工程上对”

很多 Text-to-3D 工具的目标是：

```text
Prompt → Mesh
```

重点在视觉上像不像。

而 `text-to-cad` 的路线是：

```text
Prompt → 参数 → CAD 源码 → BREP → STEP → 验证
```

重点在：

- 尺寸是否准确；
- 模型是不是有效实体；
- 孔和基准是否在正确位置；
- 零件之间是否对齐；
- 后续还能不能编辑和制造。

所以它坚持 **STEP-first**，而不是把 STL 网格当成主要结果。

STL 更像“用许多小三角形拼出外观”；STEP 保存的则是可识别、可测量的精确几何和拓扑。

### 05｜最关键的一步：生成后还要“做题验算”

代码成功运行，不等于 CAD 就一定正确。

比如参数里写了孔径 4.5 mm，最终几何也可能因为建模顺序、布尔运算或选面错误而偏离设计。

因此模型生成后，还要经历两类检查：

**确定性检查**

- 有没有有效 Solid；
- BREP 是否闭合；
- 是否存在自相交或无效拓扑；
- Bounding Box 和实际尺寸是否符合要求；
- 孔径、距离、位置是否与设计目标一致。

**视觉语义检查**

- 支架方向有没有反；
- 孔是否打错了面；
- 装配体是否穿插；
- 整体外形是否符合设计意图。

如果失败，就回到参数化源码，修改对应参数或 Feature，再重新生成和检查。

整个过程很像软件开发：

```text
写代码 → 编译 → 测试 → Debug → 再编译
```

只不过这次“编译”出来的是 CAD。

### 06｜为什么还要给几何建立 Topology？

因为 AI 后续不能只“看到一个模型”，还要能准确地指向它：

> 哪个是顶面？哪个孔属于底座？盖板和底座是否对齐？

项目会为实体、面和边建立可查询的引用。这样 Agent 才能选中具体几何对象，测量尺寸、判断法向，甚至验证装配关系。

可以把 **STEP + Topology** 理解成一座能被 AI 查询的“几何数据库”。

### 07｜它适合做什么，不适合做什么？

比较适合：

- 安装板、支架、夹具；
- 电子外壳、适配器；
- 电机座、传感器安装件；
- Robot Link；
- 尺寸明确的 3D 打印功能件。

暂时不太适合：

- 人物、雕塑等有机造型；
- 汽车外壳一类复杂自由曲面；
- 主要追求视觉效果、没有明确工程约束的模型。

它擅长的不是“随便生成一个酷炫 3D”，而是结构规则、尺寸明确、需要验证的工程零件。

### 最后

`text-to-cad` 最有启发的一点，不是让 AI 取代 CAD 内核，而是让 AI 学会使用 CAD 内核。

它背后的通用公式是：

> **LLM + 领域 Skill + 确定性工具 + 验证闭环**

LLM 负责理解和决策，专业工具负责精确执行，验证系统负责发现错误，再由 Agent 继续迭代。

这套思路不只适用于 CAD，也可能扩展到 CAE、CAM、机器人和 EDA 等对精度要求很高的工程领域。

如果 AI 生成的结果不仅能“看”，还能被测量、修改、验证和制造，AI 工程设计才算真正往前走了一步。
